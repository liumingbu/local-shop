# PRD｜local-shop 首版产品需求

版本：建议基线 v0.1；用户确认长期任务后作为开发范围。当前无功能实现。

## 1. 产品定位

面向县城、乡镇实体小店的“线上店面 + 询货记单 + 备货交付助手”。价值是将小程序、电话、微信和当面沟通形成的待办集中保存，让老板知道谁要什么、何时准备、是否交付。

不要求顾客全部改变习惯。老板即使没有顾客使用小程序，也应能通过快速代记获得价值。

## 2. 明确的模式

一个平台 AppID，多商户各自维护店名、Logo、商品、联系电话、地址、营业时间、交付说明。分享/二维码直接定位一家店，平台名与店名区别展示。一次消费者操作只属于一个租户；最近访问记录不能覆盖本次有效分享目标。

首版只邀请少量可核验商家，平台管理员负责激活租户。可预留入驻申请页面，但不做公众随意开店即营业。

## 3. 用户与权限

| 角色 | 日常行为 | 数据范围 |
|---|---|---|
| 游客 | 看已发布店铺、商品及经营联系信息 | 公开信息 |
| 顾客 | 询货、留需求、查本人记录 | 本人提交且归属当前店铺的记录 |
| 商户负责人 | 店铺、商品、需求、备货 | 授权租户范围 |
| 店员（后续启用） | 被授权的处理工作 | 服务端按成员角色限制 |
| 平台管理员 | 入驻审核、冻结、配置、异常处理 | 必须鉴权与审计，不默认随意浏览所有客户详情 |

## 4. 首版 P0

| 编号 | 功能 | 验收要点 |
|---|---|---|
| F01 | 租户及账号权限 | 两个商户彻底隔离，冻结租户不能新增公开需求 |
| F02 | 店铺资料 | 独立店名、图片、介绍、联系、营业时间与交付说明 |
| F03 | 商品与分类 | 多图、排序、上下架、规格/单位、供货状态、可选参考价格 |
| F04 | 询货 | 可对商品询问，也可仅描述/上传图片；答复不产生备货任务 |
| F05 | 顾客需求登记 | 商品清单或自由文本，数量、期望时间、自提/配送意向 |
| F06 | 老板代记 | 来源区分电话/微信/到店；没有商品库也可保存 |
| F07 | 确认备货交付 | 服务器状态机、修改留痕、取消与并发保护 |
| F08 | 待办历史 | 待回复、待备货、待取/送、超时；查询与复制成新需求 |
| F09 | 分享入口 | 本店分享参数/入口；真实二维码由微信接入阶段验证 |
| F10 | 平台基础管理 | 邀请/审核、激活/暂停商户、基础审计 |
| F11 | 使用与发布保障 | 异常、隐私、身份校验、提醒能力核验、部署交付 |

## 5. P1 候选，不自动开发

备货按规范商品汇总、打印、批量导入、店员协作、常买商品、语音/图片辅助整理、更多店铺外观。每项需实际试点需求和新增任务授权。

永不纳入本项目：在线支付、平台收款、结算/分账、担保和交易佣金。

首版不纳入：跨店搜索和推荐、跨店购物、平台流量承诺、营销/积分、精确库存流水、复杂配送调度、自动读取微信私人聊天、AI付费接口。

## 6. 顾客页面

1. 店铺首页：门店信息、分类、常用商品、询货和联系入口；默认先看内容，不强迫补资料。
2. 商品详情：多图、介绍、规格单位、可选参考价格、供货说明、询货/加入需求。
3. 询货页：文本、可选商品/图片、必要联系方式及回复方式说明。
4. 需求清单：跨商品但不跨店；数量、期望时间、交付意向；不出现支付结算。
5. 我的记录：按当前店/本人过滤，咨询与需求分组。
6. 记录详情：原始需求、商家确认结果、状态历史、联系入口。
7. 进入平台但未指定店铺：最近访问、扫码入口、商家工作台入口；不展示陌生商家推荐。

进入分享时若店铺不存在/暂停，明确提示，不静默跳到另一家店；切店要清空或分店保存草稿，避免混单。

## 7. 商户手机工作台

首页按“要处理什么”呈现，突出快速记单，而非只展示销售统计。待回复和待确认、待备货、待自提、待配送、超时事项分别可查。

快速记单：顾客称呼 + 原始需求文本为最小内容；来源默认手动。商品、电话、地址、时间可以按需要补充。已在电话确认的可明确标记确认，否则进入待沟通。顾客称呼和电话号码不等于平台用户身份。

备货视图先按单查看，每单可看商品、数量、备注和期望时间。未确认/不同单位/不同规格不汇总成误导性数量。完成仅指此次备货交付事项完成，不指平台结算。

## 8. 业务规则

- 咨询与需求独立。询货答复“有货”后，仍需明确转换或新建需求。
- 保留原始文本和商品快照，商品之后改名/下架不影响历史理解。
- 数量允许小数；单位为必要上下文；参考价可为空，不计算应付或欠款。
- 供货状态初版为常备/待确认/暂缺；不虚构精确库存。
- 期望时间与确认交付时间分开，可精确到日期+时间段；展示本地时区，后台存储清楚时区。
- 不默认承诺可以自提/配送，按商家配置开放，配送地址仅在确实必要时填写。
- 顾客重复点击必须幂等；商户同时修改须冲突检测。
- 顾客可对未确认需求申请取消；已进入备货的变更需商家处理并留痕。首版可统一提交变更意向，由商家确认，不能静默覆盖。
- 私有备注与对顾客可见回复分开。店家不能误把内部信息发给顾客。

## 9. 提醒边界

首版至少提供可靠待办刷新和醒目未处理计数。外部微信提醒需单独验证授权、模板和可达性；失败留状态，可重试，不标记已送达。没有提醒条件时不宣称“已通知商家/顾客”，试点说明检查频率并保留联系入口。

## 10. 数据与运行目标

以下是工程验收目标，不是已测试的能力：在选定的参考环境，以两个租户、每店30个合成商品、总计200条登记数据运行完整流程；以10个并发测试请求验证幂等、隔离和状态一致性。响应时间记录真实结果，部署前再根据硬件定预算，不预先声称某配置绝对够用。

没有网络/接口失败时保留可恢复草稿，不显示虚假的提交成功。重试提交仍使用同一幂等键。

## 11. 第一轮试点

建议佳琪类干货店作为首例，再找少量相近商家。所有公开演示使用合成数据和自制占位素材，不挪用真实商品图片/客户资料。

观察记单时间、实际登记比例、漏记和找历史的改善、停止提醒后老板是否继续使用。先验证“管理已有咨询”价值，不承诺帮助商家自动获得新客户。

## 12. 范围变化

品牌、收费、公开招商、自助入驻、支持特殊品类、真实消息渠道、正式运行域名和服务器均待用户决定；不影响先开发独立业务逻辑。变更写入 DECISIONS 和 ROADMAP 后再执行。
