# 给 Dot 的长期开发任务｜local-shop

你将作为本项目的长期软件开发负责人，直接完成需求落实、编码、运行、测试、修复和开发交付，不只输出方案。

仓库：`https://github.com/liumingbu/local-shop`
项目从零开始，不复用旧版佳琪程序，不假设你能读取其他对话。仓库内文档是本项目的持久化依据。

## 一、目标与首版范围

开发“面向县城实体商户的线上店面、询货记单和备货交付助手”。一个微信小程序服务多个商户，每个商户独立店名、Logo、商品、分类、需求记录和配置，不要求商户分别申请 AppID。

顾客扫码或点击分享直接进入某店，可浏览、询货、提交商品清单或文字/图片需求，登记数量、期望时间、自提/商家配送意向，查看本人记录和处理结果。

老板可在手机工作台维护店铺和商品、处理咨询、确认需求、备货、标记待自提/配送/完成；也能快速代记来自微信、电话和到店的需求。老板代记必须能不依赖商品库先保存，不强迫所有顾客改用小程序。

第一版包括：租户和权限、店铺资料、商品分类与多图、询货与需求登记、老板快速代记、备货交付状态、历史查询、店铺分享入口、基础平台管理。先邀请少量商户试用，不做复杂自助开店收费体系。

永久不做在线支付、收款、结算、分账、担保和交易佣金；首版不做全平台商品搜索、商家推荐、跨店购物、营销积分、完整进销存或 AI 自动读微信聊天。

不以“不支付”或修改文案保证免许可或审核通过。真实微信接入、备案、类目、商户资质、隐私和正式发布单独核验。

## 二、执行环境与授权

1. 只用你自己的 Dot 云电脑执行开发、文件操作、运行和测试，不依赖我的 Mac 在线。
2. 不调用 Codex Cloud、本地 Codex、ChatGPT Work，不擅自启用 GitHub Actions、Codespaces、其他云环境或外部委托任务。需要更换环境、调用付费服务或可能消耗其他产品额度时先说明并征得同意。
3. 允许在 Dot 云电脑内安装免费开发依赖、创建虚拟环境、运行隔离测试、修改本项目代码，使用已经授权的 Git/GitHub 读写分支和创建 PR。不得索取我把密钥贴进聊天。
4. 之前已经给你环境验证任务，但未取得可核验结果前，不得假定通过。本会话或其他助手能访问 GitHub，不等于你的 Git 推送和运行环境可用。
5. 实际验证仓库读写、终端、Git、Node/npm、Python、数据库能力、最小程序和测试，生成或更新 `docs/ENVIRONMENT_CHECK.md`。Docker 非必选，但 PostgreSQL 集成测试必须有真实运行条件，不能用 SQLite 冒充。
6. 云电脑只是开发环境，不视作永久在线的生产服务器。达到额度、会话或工具限制时保存进度；不承诺无限连续后台运行。

## 三、先读取与核对

按顺序读取 `AGENTS.md`、`HANDOFF.md`、`docs/PROGRESS.md`、`docs/PRD.md`、`docs/ARCHITECTURE.md`、`docs/ROADMAP.md`、`docs/TESTING.md`，再读取当前模块的模型、API、安全与外部依赖文档。

检查当前分支、HEAD、工作树、远端分支和已有 PR，不覆盖现有结果，不只看 main 就认定没有开发。文档中的初始状态可能过时，以最新远端和实际验证为准。

仓库完全为空且没有 main 时，先报告需要一个初始提交，让我在网页创建 README，或申请“仅一次初始化 main”的授权。不要为了创建 PR 自行直接写主分支。

文档包尚未导入时，先在 `chore/project-foundation` 提交文档 PR，等待我审阅合并；已有文档则不要重复生成同一套计划。

## 四、技术基线

默认采用微信原生小程序 + TypeScript、Vue 3 + TypeScript + Vite 管理后台、Python 3.12 + FastAPI、SQLAlchemy + Alembic、PostgreSQL；单仓库、模块化单体，部署交付面向一台 Linux 服务器，Docker Compose 是交付选项，不是云电脑必须支持的前提。

具体 Node、依赖和数据库版本在环境验证后锁定；记录决策。不引入 Kubernetes、微服务、Redis、消息队列等首版非必要组件。重大技术路线变更先说明理由和代价并确认。

小程序为顾客与商户的主要入口；Web 后台用于开发验证、商品批量维护和平台管理，不能用 Web 做完就声称微信小程序已完成。

## 五、开发次序与首个交付

依照 ROADMAP 的 M0—M6 推进，每次选择一个最小可验收功能。

M0：验证环境、GitHub 写入和文档基线。
M1：搭建工程、配置校验、数据库迁移、健康检查、基础测试和开发专用演示身份。
M2：先完成老板代记闭环与租户隔离。
M3：完成商品、分类、多图和公开店铺。
M4：完成顾客询货、需求登记、本人历史以及原生小程序顾客端和商户端。
M5：接入并实测微信登录、真实扫码/分享、合规可用的消息能力及隐私流程；条件缺失就记录阻塞。
M6：完成集成回归、部署与恢复说明，形成可交付试用包，等待我决定是否部署/发布。

最先证明的业务闭环：商户 A 建店 → 代记电话需求 → 确认 → 备货 → 完成 → 查询历史；商户 B 的同类操作不能看到或修改 A 的记录。

文档基线通过后，完成简短差异检查就开始 M1 代码与自动测试，不反复停留在规划。没有真实 AppID 时可先做后端和受控开发模拟，不阻塞独立模块；但不得把模拟通过写成微信真实能力通过。

## 六、核心正确性要求

- 租户隔离在服务端执行，不能只信前端 tenant_id；列表、详情、修改、附件和导出都必须覆盖越权测试。
- 咨询和确定要货分开；询货答复不能自动进入备货。状态迁移由服务端约束并留痕。
- 老板代录客户不凭姓名或未验证电话自动关联顾客账号；本人记录以经过验证的身份和归属判断。
- 数量允许小数并保留单位；不合并不同单位/规格；参考价格不是应付金额；没有真实库存就不显示假库存。
- 防止重复提交；并发修改有版本检查；保留原始需求和确认结果。
- 未授权用户可看已发布店铺和商品，但不能看客户电话地址、内部备注或私有附件。
- 开发假登录不得在生产启用；不上传真实客户资料、凭据或数据库备份。

## 七、Git 与自主推进

每个可验收功能使用独立分支并提交 PR，允许一个功能分支包含相关子任务和多次提交；不要直接写 main、自动合并、强推或改写他人历史。

完成提交后验证远端真实 SHA 和文件；本地 commit 不代表 GitHub 已收到。仅 push 成功而 PR 失败时分别报告。

普通已明确需求可继续推进，无需每个小步骤询问。主分支写入/合并、重大范围或架构变更、生产部署、真实数据删除、凭据/权限/可见性变更、外部额度或付费操作必须先确认。

前一个 PR 未合并且后续依赖它时，记录等待审阅；可以推进真正无依赖的事项，不能假装已合并或绕过主分支审批。

## 八、长期文档和真实测试

维护 `AGENTS.md`（规则）、`docs/ROADMAP.md`（阶段）、`docs/PROGRESS.md`（任务状态）、`docs/TESTING.md`（真实测试索引）、`HANDOFF.md`（短交接）、`docs/DECISIONS.md`（重要决策）。避免多个文件各自维护相互冲突的进度。

每轮记录被测代码 SHA、环境、命令、退出码、通过/失败/跳过数、脱敏日志。尚未执行写 NOT_RUN；条件缺失写 BLOCKED。

区分代码完成、测试通过、提交、PR 待审、合并、真机测试和部署。TS 检查或浏览器测试不能替代微信开发者工具/真机测试；mock 不能替代微信登录、二维码和订阅消息实测。

每轮结束前保存进度、提交可保存结果并更新交接；不能提交时提供补丁/文件和恢复说明。只有环境验证通过且真实代码、测试可核对时才报告完成对应里程碑。
