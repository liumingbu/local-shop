## 1. 目标与结束边界

在已完成 A—D 的基础上，把项目推进为“少量商户的开店准备、日常备货与沟通可进行开发验收的版本”。本轮不是重搭架构，不是继续重复登录、筛选、复制需求、启动、升级、备份和性能基准任务，也不是以测试数量增长作为目标。

本轮仅新增四个工作包：

- E：商户首次使用引导与商品清单导入。
- F：备货汇总、按单交付清单与轻量导出/打印页面。
- G：站内更新提醒与人工联系记录；外部通知仅准备可插拔边界。
- H：针对性安全审查、异常恢复与试点交付收口。

E/F 中导入、汇总、打印属于原 PRD 的 P1 候选，本任务只批准上述有限子集。不要据此把所有 P1 都纳入。店员协作、会员营销、精确库存、AI、商户收费、跨店推荐和公开自助招商不在范围内。

本轮完成后冻结新增范围，交付阶段成果并等待真实接入或用户试用反馈。不承诺无限后台工作，也不要为了让任务持续而自行增加功能。

## 2. 已知事实与不应重复的工作

开始时重新读取最新 main、开放 PR 和活动分支。上述 SHA 是核查基准，不要求回退仓库；如果已出现后续实现，先复用和核对。

A—D 已记录完成的开发工作包括：Vue/jsdom 表单事件与真实 HTTP/PG、草稿与原请求恢复、日期/方式/文字/业务号筛选、联系人地址、历史复制、正式身份与可撤销会话代码、Web 本人确认登录、聚合查询优化、启动停止诊断、旧版升级和恢复。

不得再说“正式登录代码还没有写”。准确状态是：代码及隔离测试已有证据，真实微信交换尚待联调。

真实浏览器已经完成一次有限排障，宿主 socket 权限阻塞；不要重复尝试同一种路径。jsdom 不是真实浏览器，不提供实际布局和视觉渲染证据。微信开发者工具、WXML 真正渲染、真机、微信扫码/消息、systemd 和生产部署仍分别保留未验收状态。

## 3. 执行环境和授权

只使用 Dot 自己的云电脑开发和测试；GitHub 为源码、提交和交接事实来源。不依赖用户 Mac，不调用本地/云端 Codex、ChatGPT Work、Actions、Codespaces 或其他计算环境。

可在同一云电脑、既有权限范围内使用免费开发依赖、隔离合成数据库和测试文件。不要修改宿主安全策略或建立公网隧道以规避限制。不将代码、客户资料、日志或仓库内容上传到外部 AI/扫描服务。

沿用用户已授予的常规 PR 自查、测试、合并权限。完成一个工作包后汇报阶段成果，不逐 PR 等用户审阅。先核对 AGENTS.md 与最新授权，若旧文档仍写逐 PR 待审，更新授权记录，不反复让用户批准同一件事。

生产/实际试点部署、收费、外部执行环境、真实凭据和实际权限变更、真实数据删除、真实管理员授予、微信提审均须单独确认。本轮允许实现相关受控代码并以合成账号验证，不代表允许对真实账号执行。

本项目暂无 AppID，后续再补。不得反复索取、借用旧项目 AppID 或真实凭据。仅隔离替换外部服务响应，其余应用逻辑、数据库、鉴权、状态和持久化使用真实实现。

## 4. 启动步骤与优先级

先读取 AGENTS.md、HANDOFF.md、docs/PROGRESS.md、PRD.md、ACCEPTANCE.md、SECURITY.md、DECISIONS.md、TESTING.md，以及 A—D 的专项证据。

只做增量盘点，输出一张 E—H 表：已有能力、缺口、拟修改入口、验收方式、外部阻塞。不要重写整套 PRD 或复制一套新的进度系统。

先完成 H 的小范围风险筛查。若发现可复现的鉴权、租户隔离、数据损坏或正式入口错误，先修复；否则按 E → F → G → H 收口的顺序推进。每包分成最小可验收 PR；安全与回归要求贯穿所有包。

## 5. 工作包 E：商户首次使用与商品清单导入

### E1 首次开店引导

复用现有邀请、开店账号码、本人接受和平台审核流程。增加“开店准备”入口：店铺资料 → 分类/商品 → 自提/配送说明 → 店内预览 → 已验证的分享入口。

进度从真实配置计算，不设置与实际数据脱节的假完成标记。未配置地址、联系方式或交付方式时显示适当提示，不收集不必要的顾客资料。

没有商品库也可完成店铺配置并直接记单、接收文字询货，不强迫商户导入商品才能使用。保留“稍后完善”，不要新建第二套注册/审核系统。

分享权限或微信环境未具备时明确显示“待接入”，不生成伪造小程序二维码、不把普通二维码冒充微信码、不显示已经可以真实分享。

在同一产品结构中适配干货、茶叶、五金等文字和单位示例，避免所有店铺出现“滋补品”专属业务文案。不做三套行业系统，不开发可拖拽装修平台。

### E2 商品清单导入

现有 Web 表格逐件批量保存继续复用。本轮只新增一种清晰的 CSV 模板导入入口，不扩展任意 Excel 宏、压缩包、外部网站采集或自动下载远程图片。

模板字段建议为：商品名称、分类、规格、单位、参考价格（可空）、供货说明、排序和商品介绍。字段及枚举必须与现有模型一致；不加入支付金额、欠款和精确库存流水。

流程：选文件 → 解析/预校验 → 按行预览错误和疑似重复 → 用户确认 → 创建商品草稿 → 显示每行结果。

要求：

1. 限制文件大小、行数、列数和单元格长度；建议首版最多 200 行，文件阈值由测试确定并配置，不是系统承诺的容量。
2. 默认只新增草稿，不自动发布、不静默覆盖原商品、不按同名直接替换。
3. 新分类先列出预览并由用户确认；同名多规格不能被误判成同一个商品。
4. 复用现有幂等和版本规则。每行明确成功/失败/尚未执行；中断后只继续未完成部分，不重复新增已成功内容。
5. 实际写入后再次导入相同内容，提示疑似重复并要求明确选择；不声称一个幂等键能解决所有不同批次重复问题。
6. 将数据按文本处理，不执行公式、宏或外部引用；导出错误清单也要防公式注入。
7. 不接收文件中自带 tenant_id 作为授权依据。导入任务、原文件、错误报告和结果都只属于当前授权店铺。
8. 解析失败不改变商品；已导入的部分不自动回滚删除。允许在确认后按既有归档机制处理错误导入，但不新增默认永久删除。

### E 验收

至少覆盖一个从零配置店铺的合成商户、一个没有商品也能记单的商户，以及两个租户的导入隔离。覆盖中文/逗号/引号/换行、空价、同名不同规格、错误单位、超限、重复批次、半途断开及重试。

交付真实代码和 Web 事件 + HTTP/PG 证据；原生引导页面给出逻辑和资源检查结果。视觉/微信测试条件缺失继续标 NOT_RUN/BLOCKED。

## 6. 工作包 F：备货与交付清单

### F1 按单与按商品两个视图

复用 B 包的日期、方式、状态筛选和确认数据，新增“今日备货”入口，而非重复实现筛选或另建订单系统。

按单：展示已确认的商品明细、数量/单位、明确交付时间或时段、交付方式与必要备注。

按商品：只汇总同一租户中符合条件、经过明确确认的明细。至少按商品标识、确认时规格和单位分组；“盒/袋/斤/克”不同则不合并，不仅按商品名分组，不自动换算。

未确认、取消、已完成项默认不进入待备总量。取消申请处理中单独标记“需核对”，避免把待决定事项直接当确定数量；原始自由文本和无法结构化的需求单列为“需人工核对”，不进行 AI 猜测。

汇总必须能展开追溯到组成它的每一单。展示统计范围、生成时间；在看清单期间记录被修改时，提示刷新，不把旧导出当实时状态。优先派生查询，避免另存一套容易不一致的数量台账。

### F2 清单输出

只做两种有限模板：

- 备货单：商品、数量/单位、业务号和必要取货标识；默认不包含完整电话、配送地址或内部备注。
- 配送/自提清单：在现有权限内，根据用途显式选择必要联系方式；导出前清楚提示所含个人信息。

先实现受鉴权 Web 清单、文本/CSV 下载以及轻量打印样式。不接热敏/蓝牙打印机，不新增专业打印服务，不为了 PDF 拉入大型独立渲染基础设施。

如果浏览器不能运行，只验证生成内容、转义、鉴权、字段选择和打印样式源码；真实分页和纸面效果标记未验收，不得伪造打印截图。

导出仅限本店授权操作，记录操作者、用途和范围，不记录明文内容或令牌。文件不能长期以无鉴权固定 URL 暴露。限量导出，防止跨店或一次性全库导出。

不因为“已经打印/导出”自动将事项变成“已备好/已送达”。仍由老板明确更新原业务状态。

### F 验收

覆盖相同商品不同规格/单位、原始自由文本、取消/修改后重新汇总、不同店同名商品、导出脱敏和越权拒绝。确认 CSV 的文本字段不会变成可执行公式，HTML 不解释用户输入为标签。

## 7. 工作包 G：站内更新与人工沟通记录

目标是让老板知道有新需求，让顾客知道店家有回复，同时避免把“站内看见”误写成“微信已经通知”。不另做即时聊天系统。

### G1 站内更新

优先复用现有状态、回复、审计和事件记录；只增加必要的收件人/已读游标等数据，不为每种消息再建一套业务状态。

面向老板：新需求、需要回复的询货、取消/变更意向。

面向顾客：对本人公开的询货回复、商家确认或变更结果、备好等必要状态变化。

严格区分：

- 未读：本人尚未查看的新变化。
- 待处理：业务上还没有完成的动作。

读过消息不等于已经处理需求，商家看过也不能自动标记顾客已读。一店读取不清除另一店提醒；切账号清除私有可见信息，服务端校验真实归属。

页面可见时做有界刷新，失败退避；页面隐藏、退出登录和账号/店铺切换时取消或失效化旧请求。不存在持续后台执行能力时，绝不承诺关闭小程序后自动轮询或响铃。

业务事件与站内提醒保持一致：重复请求不产生重复提醒；事务回滚不产生有效提醒；重启后可继续显示未处理信息。清单跳转时重新鉴权，不能因掌握消息 ID 读取他人记录或私图。

### G2 人工联系记录

允许商家明确记录“已电话联系”“已微信联系”“未联系上”与简短备注。点击拨号或复制文案本身不能自动算已联系成功。状态和备注默认内部可见，顾客只看到已明确对外公开的确认结果。

可由当前确认结果生成一段待商家核对的联系文本，默认不包含其他顾客、内部备注或完整敏感地址。由商家明确复制/发送，不自动读取或控制私人微信聊天。

### G3 外部提醒边界

保留可插拔的外部通知接口、业务事件及调用结果模型。没有本项目 AppID、模板和相关核验时默认关闭，不自动发微信、短信、邮件或企业微信，也不新增付费渠道。

测试替身可模拟未配置、拒绝、超时、调用明确失败、接口接受及结果未知。必须区分“请求已接受”“真实送达”“用户已读”，没有对应证据的状态不能自行填充。结果未知不得无限重试；同一业务事件有去重标识，不承诺第三方端严格只发送一次。

微信具体 API、模板资格和授权行为在接入时查官方文档及本项目后台；目前不编造限制、模板 ID 或字段。外部接口不可核实时，不阻塞 G1/G2。

## 8. 工作包 H：有针对性的安全与故障恢复收口

H 不是重新写鉴权、重新造测试框架或无限“加固”。先核对已有测试，只补没有覆盖的具体风险。每项问题要有代码位置、可复现条件、影响、最小修复、修复前后测试。

### H1 优先检查的现有代码风险点

核查基准中的 formal_auth.py 根据 request.client.host 计算登录及网页确认限流；__main__.py 配置 proxy_headers=False。

这不是本次已复现的漏洞结论，但值得验证：真实 Nginx→API 拓扑是否会将多个用户识别为同一回环地址而共享限流？是否有人能伪造代理头绕过限流？

要求在同一云电脑内用合成流量复现代理路径。不要简单开启对所有来源 X-Forwarded-For 的信任；不要因此放宽开发身份的本机限制。按照明确可信代理边界修复，实际生产代理设置仍待授权部署验证。

核查 Web 本人确认登录：确认码有时效、次数限制、明确用户动作，轮询秘密不泄漏；并发确认/领取不会串账号；失效会话不能读私图和导出；正式入口不接受演示身份；平台邀请和开店账号码不会造成越权。

### H2 新功能带来的边界

- CSV 导入解析、导出公式/HTML 注入、跨租户任务编号和文件读取。
- 站内消息深链接、私图、统计汇总、导出均重新服务端鉴权。
- 用户上传文件的实际类型、尺寸与容量边界；复用已有解码/压缩/元数据清除，而不是重复实现。
- 原生/Web 草稿、日志、错误信息、源码包中不泄漏令牌、登录码、电话地址和私图。
- 客户记录不凭姓名/手填电话自动关联账号。
- 正式模拟模式、演示数据、配置默认值、发布检查不能绕过外部未验收门槛。

### H3 故障与数据增长

基于现有 maintenance_check 和恢复工具增量完善，不重写。仅生成只读的孤立文件、过期会话/限流记录、容量增长及备份情况报告；不启用真实数据定期清理，不自动删除幂等或审计历史。

用隔离合成环境模拟进程中断、数据库短时不可用、文件写失败和相应恢复，证明重试不重复记单、不误送提醒、不产生可公开的越权附件。不能改宿主权限来模拟故障；可使用受控故障注入。

新增迁移须验证旧版合成数据向新版本升级；继续复用既有启动/诊断/恢复演练。性能只对本轮发生变化的导入、汇总、消息路径做有界基准，不重复大规模无目标压测。

## 9. 文档、交付与事实分级

继续用 PROGRESS.md 作唯一进度台账，更新原 PRD 中被本任务批准的 P1 子集、ROADMAP、DECISIONS、TESTING 和 HANDOFF。不另造另一套项目管理目录。将本任务放进 docs 作为范围来源。

每个工作包输出：

1. 用户可见的入口和变化。
2. 明确的合成验收场景及执行命令。
3. 被测代码 SHA、环境、真实退出码、失败修复记录和脱敏证据。
4. API/PG、jsdom、原生逻辑、真实浏览器、微信工具/真机分别结论。
5. 实际 PR 与合并后的远端核验；不能把本地提交当成远端提交。

最终额外交付：商户首次上手指南、导入模板说明、备货/沟通指南、试点场景清单与反馈表、精确 SHA 源码包及校验。资料应跟当前 UI 入口一致，不编造运行截图，也不要复制历史交付报告并改日期。

试点场景至少覆盖三个合成租户：固定规格商品、称重/规格浮动商品、图片/文字询货。普通顾客的真实体验评价不能用脚本冒充；报告写“合成旅程验证”，不是“真实商户试用通过”。

## 10. 完成条件与停止规则

本阶段可以完成代码、真实服务端与可用测试条件内的验证；以下保持独立外部验收项：真实浏览器布局/操作、WXML 渲染与微信开发者工具、iOS/Android 真机、真实微信身份/分享/通知/隐私、systemd/生产生命周期、经营与平台发布条件。

只要 E—H 各项实现与证据完整，并清楚保留外部阻塞，就交付本阶段，不再自行扩展 CRM、收费套餐、商城、支付、AI 或店员协作。

若一个子项受限，注明最小条件并推进其他无依赖项；如果所有剩余任务均需外部条件或用户决策，保存交接并停止。不要重做 A—D，也不要反复催 AppID。

现在先核对最新仓库，完成最小差异盘点及 H1 的具体风险核对；没有阻断性问题就开始 E1。不要只回复计划。
